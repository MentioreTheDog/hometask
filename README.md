# Обнаружение мошеннических аккаунтов в сети Ethereum

Проект по бинарной классификации Ethereum-аккаунтов на основе агрегированных ончейн-метрик активности. Решает задачу автоматического выявления мошеннических кошельков до того, как они нанесут ущерб пользователям бирж и кошельков. Продолжение темы Web3: от описательного анализа ончейн-активности — к предсказательной модели.

---

## Датасет

- **Источник:** [Ethereum Fraud Detection Dataset](https://www.kaggle.com/datasets/vagifa/ethereum-frauddetection-dataset) на Kaggle (автор vagifa). Файл получен через зеркало на GitHub — [eltontay/Ethereum-Fraud-Detection](https://github.com/eltontay/Ethereum-Fraud-Detection), так как исходная страница Kaggle требует авторизации для скачивания.
- **Размер:** 9841 строка (уникальный Ethereum-аккаунт), 51 столбец
- **Период / охват данных:** снимок агрегированной статистики по аккаунтам, собранный по состоянию на 2021 год (не временной ряд)
- **Ключевые признаки:**
  - `Sent tnx` / `Received Tnx` — число отправленных/полученных транзакций
  - `Time Diff between first and last (Mins)` — продолжительность жизни аккаунта
  - `Avg min between sent/received tnx` — средний интервал между транзакциями
  - `total ether balance`, `avg val sent`, `avg val received` — объёмы операций в ETH
  - `ERC20 ...` (группа столбцов) — то же самое, но для операций с ERC20-токенами
  - `Address`, `Index` — идентификаторы (удалены при подготовке данных, не используются моделью)
  - **`FLAG`** — целевая переменная: 0 = обычный аккаунт, 1 = мошеннический (баланс классов 78% / 22%)

**Как определялась метка `FLAG`:** адреса, помеченные как мошеннические, взяты со страницы Etherscan `etherscan.io/accounts/label/phish-hack` — официального тега блок-эксплорера для адресов, связанных с фишингом и взломами (сообщество Ethereum относит сюда фейковые ICO, схемы Понци, зеркальные фишинговые сайты и подобное). Разметка получена независимо от признаков модели — таким образом, найденные моделью закономерности не являются artefact'ом самой разметки.

## Методология

1. Загрузка и первичный анализ данных (EDA): размер, типы, группы признаков, пропуски
2. Очистка данных: удаление идентификаторов и высококардинальных категорий, заполнение пропусков ERC20-метрик нулями (пропуск = отсутствие ERC20-активности), удаление дублей и константных столбцов
3. Визуализация ключевых зависимостей: баланс классов, сравнение групп по активности и суммам ETH, корреляция признаков с `FLAG`
4. Построение модели: **Logistic Regression** (baseline) и **Random Forest** (с `class_weight="balanced"` и подбором гиперпараметров через `GridSearchCV`)
5. Оценка качества по метрикам: **Accuracy, Precision, Recall, F1, ROC-AUC** — акцент на F1 и ROC-AUC из-за умеренного дисбаланса классов (78/22)

## Результаты

| Модель | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| Logistic Regression | 0.569 | 0.269 | 0.822 | 0.405 | 0.792 |
| Random Forest (baseline) | 0.956 | 0.953 | 0.795 | 0.867 | 0.987 |
| **Random Forest (подобранный)** | **0.958** | **0.923** | **0.834** | **0.876** | **0.986** |

- Модель **Random Forest** достигла **F1 = 0.876** и **ROC-AUC = 0.986** — более чем вдвое лучше базовой Logistic Regression (F1 = 0.405)
- Все ключевые корреляции признаков с `FLAG` отрицательные: чем короче история аккаунта и чем реже он получает транзакции — тем выше вероятность мошенничества
- Топ-признаки по важности в Random Forest (`Time Diff between first and last`, `total ether received`, `avg val received`) совпадают с топ-признаками по корреляции — два независимых метода подтверждают друг друга

## Ограничения

- Датасет ограничен по периоду — данные собраны по состоянию **до 2021 года**, модель может хуже распознавать более новые схемы мошенничества (например, через DeFi-протоколы или NFT)
- Данные — статичный "снимок" агрегированных метрик по каждому аккаунту, а не временной ряд отдельных транзакций
- Разметка `FLAG` основана на списке известных фишинговых/скам-адресов Etherscan на момент сбора данных; страница с этой разметкой на Etherscan на данный момент удалена, повторно собрать данные тем же способом нельзя
- Умеренный дисбаланс классов (78/22) требует аккуратной интерпретации Accuracy — в проекте сделан акцент на F1 и ROC-AUC по этой причине
